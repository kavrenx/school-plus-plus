# Исходные измерения открытия дневника

27 октября 2026, исходный код опубликованного `0855379`. При съёмке исходного
профиля код приложения не менялся. Затем по подтверждённой задержке подготовлен
локальный пакетный импорт; его результат приведён в конце отчёта.

## Среда и границы

- Node.js 24.19.0 на текущем ПК; встроенный Chromium для браузерного прогона.
- Синтетический снимок: 8 недель / 240 уроков либо 36 недель / 1080 уроков,
  шесть уроков в день, два предмета, числовые пары `9/9` и домашние задания.
- Для браузера собрана отдельная минифицированная версия с теми же Vite inputs,
  `VITE_APP_MODE=local`, пустой process-only Supabase-конфигурацией и base `/`.
  Сервер отдавал её по домашней LAN. Снимок передавал синтетический desktop bridge
  с обычными проверками origin/source/requestId; установленное расширение не нужно.
- Временные инструменты, снимки и сборка находятся только в игнорируемой `.vite/`.
  Плагин измерений добавлял отметки к копии `script.js` при отдельной сборке;
  исходный composition root, store, production build и публичный сайт не правились.
- Маркеры показывают готовность DOM после `init()`. Скрытая вкладка не дала paint
  entries, поэтому эти числа не являются FCP/LCP или временем видимого кадра Safari.
- Это одиночные контрольные прогоны без ограничения CPU/сети. Реальный iPhone,
  внешний интернет, Auth, device RPC и чтение облачного снимка здесь не измерены.
  Встроенный снимок увеличивает HTML, поэтому сетевой результат нельзя напрямую
  переносить на production. Браузерный кеш ресурсов отдельно не сбрасывался.

## Подтверждённая повторная работа

В [script.js](../script.js) `importJournalEntries()` вызывает
`store.saveJournalEntry()` для каждого импортированного урока, в том числе при
повторном открытии неизменившегося дневника. Это происходит до `init()`.

В [journal-store.js](../js/journal-store.js) каждый такой вызов:

1. Читает, разбирает и нормализует целый документ через `getDocument()`.
2. Ищет прежние сущности урока в коллекциях и заменяет их.
3. Сериализует и сохраняет целый документ через `saveDocument()`.

Число записей равно числу уроков. По мере роста документа возрастают стоимость
каждой записи и суммарная сериализация. При повторном открытии документ уже
заполнен целиком, поэтому обработка может быть дороже первого импорта.

## Подготовленная локальная правка

`createJournalStore()` получил необязательный локальный `saveJournalEntries()`.
`script.js` использует его в student import, включая повторное получение снимка;
у репозитория без этого метода остаётся прежний fallback. Метод заранее
нормализует весь вход, сохраняет последнюю запись каждой пары урок/ученик, один
раз удаляет старые сущности целевых пар и один раз сохраняет обновлённый документ.
Общие работы уроков и итоговые записи остаются нетронутыми. Прежняя одиночная
операция использует старый путь удаления, её поведение не менялось.

Новая проверка результата сравнивает пакетный и поштучный импорт всех полей
(кроме различающегося времени операции), пары одинаковых оценок, pass/fail,
материалы/endpoint, посещение, чужие пары, миграции v2/legacy, ошибку хранения,
пустой массив, некорректный элемент и последующее одиночное изменение.
Schema/storage IDs и HTTP-контракт прежние. Teacher-mode UI и его вызовы не менялись.
372 теста, lint, format:check и cloud build прошли. Это пока локальное изменение.

## Следующий этап: стартовые зависимости и сетевые ожидания, 28 октября

Пакетный импорт выше уже опубликован 27 октября (`bb795d4`), пользователь
подтвердил работу на настоящем дневнике. Следующие изменения пока локальные.

### Отложенная загрузка QR

Анализ cloud-сборки с тем же Vite base подтвердил: все 27 модулей пакета `qrcode`
входили в стартовый chunk `userscript-auto-sync`, поскольку `device-controller.js`
статически импортировал библиотеку. Название chunk не определяет всё его содержимое.
Генератор нужен только при создании кода подключения другого устройства.

Статический import заменён на dynamic import внутри действия создания QR.
При первом нажатии кнопка показывает состояние загрузки. При ошибке загрузки
сохраняются кнопка и возможность повторить попытку; серверный pairing ещё не создан.
Закрытие/повторное открытие окна во время загрузки отменяет старое действие до
серверной операции. Auth, RPC, подтверждение доступа, срок кода и сканируемая
ссылка не менялись.

| Стартовый JavaScript, 9 файлов | До     | После  | Разница |
| ------------------------------ | ------ | ------ | ------- |
| Размер, байт                   | 534922 | 513203 | −21719  |
| Gzip, байт                     | 164289 | 156189 | −8100   |

Это около 4% исходного JS / 5% gzip. CSS прежний. Расчёт gzip выполнен одним
`gzipSync` для обоих наборов; это оценка файлов, а не фактического HTTP-трафика
конкретного браузера. QR-chunk теперь динамический и отсутствует в стартовых
HTML script/modulepreload ссылках. Общий объём кода не исчез: он загружается
при необходимости. Сокращение размера не доказывает заметного сокращения
времени входа при тёплом кеше или на быстрой LAN.

## Удаление ожидания desktop bridge в мобильном cloud fallback

После успешного отчёта `lazy-qr-local` (53 мс, устройство не указано) пользователь
уточнил порядок работы: обычные локальные прогоны Codex выполняет сам; ручная
проверка нужна только для невоспроизводимого сбоя или специфики настоящего
Safari/установленного расширения. Новый ручной тест для этой правки не запрошен.

### Подтверждённая причина и границы изменения

В `script.js` после веток linked и Userscripts-кеша одновременно начинались
чтение облачной копии и ожидание desktop `postMessage`-снимка до 2500 мс.
Первым всё равно ожидался desktop-запрос. На Apple mobile в проекте используется
другой, Userscripts DOM-протокол, поэтому это ожидание в cloud fallback было
бесполезным. Кешированные Userscripts и linked данные и раньше обходили этот путь.

`requestStartupExtensionSnapshot()` в `js/startup-diary-source.js` сразу возвращает
отсутствие desktop-снимка на Apple mobile, используя существующее определение
платформы. На ПК, Android и при неизвестной платформе остаётся прежний запрос с
тайм-аутом 2500 мс. Не менялись проверки Auth, owner/linked, запросы к БД,
приоритет desktop-снимка на ПК, форматы кешей и оба протокола. Все остальные
вызовы `requestExtensionSnapshot()` сохранены.

### Воспроизводимое сравнение настоящей сборки

Изолированная сборка с настоящим Supabase SDK, 1080 синтетическими уроками,
фиктивным publishable key и перехваченным fetch к несуществующему тестовому
хосту. Любой неожиданный внешний запрос блокируется. Каждый ответ Auth/RPC/REST
искусственно задержан на 200 мс. Измерительные маркеры вставлены Vite-плагином
только в эту сборку; обычный сайт не получает тестовый отчёт или фиктивную сеть.
Исходный composition root взят из `bb795d4`, текущие остальные модули одинаковы
в двух сборках, включая подготовленную ранее отложенную загрузку QR.

| ----------------------------- | ---------------- | ---------------- | -------------------------- |
| Мобильный владелец без кеша   | 3497, 3500, 3515 | 1838, 1839, 1839 | 1 → 0                      |

коэффициент для каждого входа на iPhone нельзя. На очень медленном сервере
выигрыш может отсутствовать, поскольку облачные запросы сами займут больше 2,5 с.

### Проверки и оставшиеся наблюдения

388 тестов, lint, format:check и cloud build прошли. Новые проверки покрывают
отсутствие desktop-сообщений/таймеров на Apple mobile, desktop/Android/неизвестную

обработчика при ответе/тайм-ауте. Учительский журнал и сервер не менялись.

Трасса показала, что первый Auth и публичный site status уже идут параллельно.
Их перестановка сама по себе не является доказанной оптимизацией. Видны повторные
Auth-проверки, в том числе параллельные для activity и device access, но они пока
сохранены: проверка доступа важнее сокращения счётчика запросов. Cloud repository
по-прежнему ждёт историю изменений; изменение этого поведения потребует отдельной
проверки порядка outbox, смены владельца и обновления UI.

## Общий пакет с фоновой историей, 29 октября

По просьбе пользователя QR, мобильный cloud fallback и работу с историей готовим
как один выпуск сайта. Проверки отдельных изменений остаются раздельными.

### Дневник раньше истории, прежняя очередь сохранений

`createDiaryHistoryRepository.loadProgressively()` даёт два результата:
изолированную раннюю копию снимка и завершение прежней операции с историей.
Обычный `load()` прежний. Outbox, history, последующие save/remove сохраняют
последовательность общей очереди; дополнительные сетевые запросы не добавляются.
Показ дневника больше не зависит от завершения необязательной истории.

`createStartupDiaryLoad` дополнительно проверяет владельца при использовании
обеих фаз. Смена A → B → A тоже отменяет старый результат, обновление токена
того же пользователя — нет. Наблюдатель снимает подписку после завершения или
окончательного ухода со страницы; BFCache не отменяет чтение, но при применении
после возобновления владелец проверяется заново. В UI история получает состояния
загрузки/недоступности с сохранёнными карточками. Её догрузка обновляет только
историю и счётчик, сохраняя выбранную дату, поиск и открытые инструменты предмета.

### Сравнение всего пакета

Тот же изолированный стенд: Chromium, настоящая сборка/SDK, Apple-mobile признаки,
1080 синтетических уроков, по 200 мс на ответ. Три последовательных прогона каждого
варианта на одном браузере; времена — маркер окончания init, не фактический paint.

| Мобильный fallback                   | Прогоны DOM, мс  | Медиана, мс |
| ------------------------------------ | ---------------- | ----------- |
| Исходный composition root            | 3428, 3434, 3534 | 3434        |
| Без ожидания desktop bridge          | 1758, 1766, 1815 | 1766        |
| Плюс ранний показ снимка без истории | 1334, 1350, 1413 | 1350        |

В этом сценарии история добавляла примерно 416 мс к медиане. Полный пакет дал
3434 → 1350 мс; это не гарантия для реальной сети или любого входа на iPhone.
ПК с расширением: 926 → 932 мс; linked-кеш: 533 → 530; Userscripts-кеш: 969 → 1003
(по одному контрольному запуску, не доказательство небольших эффектов).
Видимый текст dashboard совпал во всех сравнениях, необработанных ошибок не было.

Отдельно в браузере удержан ответ истории до ручного освобождения тестовым
контролом: дневник уже работал, окно истории показывало загрузку, после ответа
появилась карточка с сохранённым поиском. Ошибка history RPC не скрыла шесть
строк дневника и сохранённую карточку. Стенд не обращается к live Supabase,
его fake конфигурация/данные и отчёт отсутствуют в обычной сборке.

Новые unit/DOM-проверки покрывают обе фазы и их ошибки, изоляцию ранней копии,
порядок outbox/history/save, отмену, чужой UID, A → B → A, отказ чтения сессии,
повторные вызовы, очистку подписок и сохранность поиска/инструментов/кеша в UI.
Фактическая статистика итоговой проверки фиксируется в PROJECT_CONTEXT.md.
Реальный Safari этим стендом не заменяется, новый ручной прогон пользователя
для обычной локальной регрессии не запрашивался.
