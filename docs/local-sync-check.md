# Локальная проверка готовности Userscripts

Эта проверка относится к задержке `bridge_ping` на iPhone. Она использует
реальный DOM-v2 клиент сайта и отдельный локальный тестовый Userscript с прежними
GM namespace и sources. Проверяется только ping/совместимость; сбор дневника,
облачная авторизация и запись в Supabase не запускаются. Успешный ping не
подменяет последующую проверку полного production-потока.

## Запуск на компьютере

В PowerShell из корня проекта (Node 22.12+), указать текущий приватный IPv4
компьютера в домашней Wi-Fi сети. Адрес VPN не подходит:

```powershell
$syncCheckHost = '<IPv4-компьютера>'
$env:VITE_PAIRING_ORIGIN = "http://${syncCheckHost}:5174"
npm.cmd run dev -- --host $syncCheckHost --port 5174 --strictPort
```

Для полного локального прохода с просмотром дневника перед запуском также задать
в этом PowerShell `$env:VITE_APP_MODE = 'local'`, `$env:VITE_SUPABASE_URL = ''` и
`$env:VITE_SUPABASE_PUBLISHABLE_KEY = ''`. Тогда весь dev-сервер работает без
облачных сервисов; реальные env-файлы и настройки production не меняются.

Изменяется только окружение этого процесса; реальные `.env*` править не нужно.
Сервер остановить `Ctrl+C`. При смене IP/порта обновить тестовый установщик.
Сервер привязан только к указанному домашнему адресу, а не ко всем VPN-интерфейсам.
При отказе доступа/firewall проверить настройки вместе с пользователем, не
отключать защиту автоматически.

## Проверка на iPhone

1. Подключить оба устройства к одной Wi-Fi сети. Открыть в обычном Safari
   `http://<IPv4-компьютера>:5174/dev/userscript-readiness.html`.
2. Через ссылку на странице установить «School++ — тест на iPhone» и разрешить
   Userscripts работать на локальном адресе. Обычный production-скрипт не менять.
3. Вернуться на страницу и выполнить полную перезагрузку. После установки нужна
   именно перезагрузка документа, а не только кнопка повторного ping.
4. Скопировать отчёт. Повторить полную перезагрузку 2–3 раза. Проверить и повторный
   ping на уже открытой странице. Затем выключить локальный тестовый скрипт.

Отчёт содержит только исход, длительность ping, число запросов и ограниченный
код ошибки/факт наличия маркера при отказе. Нет URL, request ID, данных дневника
или автоматической отправки.

## Что ожидается и что не доказано

До изменения первый ping, отправленный до инъекции, ждёт до 2000 мс, прежде чем
повториться. Теперь изменение существующего маркера готовности вызывает один
немедленный повтор **в пределах того же тайм-аута**, с тем же ID. Ответ по-прежнему
проверяется по документу, origin, source, ID и совместимости; маркер не является
подтверждением готовности сам по себе. Другие команды не повторяются.

Отсутствие ответа всё ещё ограничено тремя попытками по 2 секунды. Это изменение
ускоряет обнаружение запустившегося скрипта, но не исправляет причины полного
отсутствия инъекции Safari. Реальное сокращение двух пауз по 2 секунды нужно
подтвердить на iPhone. Если скрипт уже готов до первого ping, запрос один.

Страница `dev/userscript-readiness.html` не входит в Vite production inputs;
её не нужно публиковать. `schoolpp.user.js` сохраняет только production-адреса.
Тестовый `/schoolpp-test.user.js` выдаётся только dev-сервером и хранит попытки
отдельно от production. Полный импорт/облачное сохранение уже проверяются
unit/DOM/VM/SQL suites; эта страница проверяет дополнительную границу реального
Safari и Userscripts, не имитируя успешную синхронизацию.

## Контрольный синтетический замер

26 октября 2026, локальный встроенный браузер, настоящий DOM-v2 client/runtime,
искусственная инъекция через 150 мс, три чередующихся прогона. Старый клиент из
`b3f6bfe` ответил через 2006/2002/2015 мс, новый — через 155/155/155 мс.
Медиана 2006 → 155 мс. Ни GM-хранилище дневника, ни Supabase не использовались.
Это проверка ожидания при заданной задержке, не замер реального Safari или
полной синхронизации. Восемь новых unit/DOM-тестов проверяют ограничение повтора,
чужие origin/source/ID, несовместимость, параллельные ping, fallback и очистку
наблюдателей/таймеров; полный набор на этом этапе — 341 тест.

## Полный локальный проход после проверки связи

Пользователь подтвердил реальный iPhone ping за 0–1 мс с одним запросом. Это
подтверждает уже готовый Userscripts, но не измеряет позднюю инъекцию.

1. Открыть в той же вкладке Safari
   `http://<IPv4-компьютера>:5174/dev/userscript-sync.html?syncTiming=1`.
2. Нажать «Запустить синхронизацию» и при необходимости войти в госдневник.
   Повторная установка локального скрипта 0.1.1-test не требуется.
3. Дождаться возврата, скопировать замеры, открыть локальный дневник и проверить
   несколько предметов/дат. Данные сохраняются только в существующем `TEST_CACHE`
   этого локального origin. Основной owner-scoped кеш не используется и не меняется.

Dev middleware перенаправляет GET `/userscripts-setup.html?returned=1` в
`/dev/userscript-sync.html?returned=1&syncTiming=1`: так старый локальный v1
установщик не попадает в production-страницу с v2-клиентом. Переход фиксированный,
параметры чужого URL не передаются. Middleware не работает на опубликованном сайте.
Production installer, протоколы, allowlists, GM tab binding и форматы не менялись.

`check: local-roundtrip`, `cloud: not_run` явно отличают отчёт от облачной
синхронизации. `local_save` включает строгий разбор/адаптацию через общий
`saveUserscriptCache`; отдельно CPU разбора не измеряется. Нет искусственных
задержек анимации production-контроллера, Auth/device access и cloud save, поэтому
итоговые времена не являются прямым сравнением полного production-потока.
`start_total` и `return_total` не включают загрузки страниц и пользовательский вход.

Результат сначала проверяется на полноту и сохраняется, только затем выполняется
ack. Отказ хранения/неполный экспорт не очищает GM-результат. Отказ ack оставляет
проверенную локальную копию и pending для повторного получения. Истёкшая попытка
и отказ привязки вкладки блокируют импорт. После проверки выключить тестовый скрипт.
