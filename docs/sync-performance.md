# Измерение Safari-синхронизации

Первый этап оптимизации сохраняет внешний вид обычного потока, учительский режим,
форматы данных, owner checks, проверки полноты и DOM-v2 протокол Userscripts.
Live Supabase не меняется. Для разработки сначала используются локальные проверки
и синтетические данные. Проверка на реальном iPhone возможна через отдельный
тестовый установщик в локальной сети либо через согласованную публикацию сайта,
когда пользователь дистанционно. Обновлять production Userscript для этого этапа
не требуется; его allowlist не расширяется ради локального теста.

## Что изменено

- Страница синхронизации использует один `createUserscriptDiaryStorage` для
  importer и controller. Один и тот же текст экспорта разбирается один раз.
  При каждом чтении заново проверяются фактический storage envelope, owner и
  `savedAt`; изменение текста запускает новую полную проверку. Внешние вызовы
  получают копии, поэтому не могут изменить закешированный результат проверки.
- На возврате receive отправляется только после успешного ping/compatibility.
  Safari может запустить скрипт на document-idle позже модуля страницы: ping имеет
  повторные попытки, а ранний одноразовый receive потерялся бы до установки
  слушателя. Проверки origin/requestId/tab не меняются. Это воспроизводится
  локальным тестом с настоящими DOM-v2 client/runtime и отложенной инъекцией.
- Чтение копии и очистка предыдущей попытки перед новым start также перекрываются.

Этап ожидания готовности проверен локально: при поздней инъекции клиент
наблюдает существующий маркер ready/unsupported_manager и один раз
повторяет только ping, не дожидаясь 2-секундного тайм-аута. Маркер не заменяет
ответ протокола и совместимость. Тайм-ауты и три резервные попытки сохранены;
start/receive/ack/cancel не повторяются по маркеру. Инструкция проверки без
сбора дневника и Supabase — [local-sync-check.md](local-sync-check.md).

Реальный iPhone прошёл и локальный round trip через тестовый v1-скрипт:
ping 2 мс до перехода и 1 мс после возврата, collection 1104 мс,
receive 16 мс, local_save 23 мс, ack 9 мс; start_total 8 мс, return_total 49 мс.
Облако не запускалось (`check: local-roundtrip`, `cloud: not_run`). В этом запуске
двухсекундных пауз нет, но это не прямое сравнение с production-контроллером:
нет Auth/device access, cloud save и его анимационных задержек, другой локальный
кеш. Сам по себе быстрый ping не отделяет эффект observer от более ранней
инъекции на LAN. Пользователь также подтвердил корректность предметов, дат и
оценок в открытом локальном дневнике. Полный cloud-поток с новой правкой ещё
не измерен.

## Как включить замер

После разрешённой публикации открыть на iPhone в той же вкладке Safari:
`https://schoolpp.com/userscripts-sync.html?syncTiming=1`.

1. Выполнить синхронизацию обычным способом, при необходимости войти в госдневник.
2. После успеха диагностический режим остановится перед открытием дневника.
   Нажать «Скопировать замеры», затем «Открыть дневник».
3. Передавать для анализа только скопированный отчёт. Экспорт дневника не нужен.
4. Повторить 2–3 раза при одинаковом соединении. Отдельно отметить, потребовался
   ли вход в госдневник, и длительность всего пути по секундомеру.

Обычные посещения без включённого замера автоматически открывают дневник как
раньше. Диагностика сохраняется в sessionStorage этой вкладки до 15 минут от
начала попытки и переносится через возврат Userscripts без смены протокола.
Выключить её можно параметром `?syncTiming=0` при следующем запуске.

## Состав отчёта

Только версия, грубый результат и ограниченный список названий этапов,
длительностей в миллисекундах и статусов выполнения. Нет UID, идентификаторов
попытки/ученика, URL, имени, класса, отметок, заданий, токенов, raw export или
текстов ошибок. Автоматической отправки отчёта на сервер нет. Чтение отчёта
отбрасывает неизвестные поля и названия этапов.

- `start_total` — подготовка на School++ до передачи управления Userscripts.
- `bridge_*` — связь страницы с Userscripts.
- `auth_user`, `device_access` — подготовка Auth и проверка роли устройства.
- `collection` — время сборщика из проверенного отчёта установленного скрипта.
  Оно не включает ожидание пользовательского входа перед запуском сборщика.
- `export_parse`, `local_save`, `cache_read` — локальная обработка.
- `cloud_save` — полное ожидание облачного сохранения с тайм-аутом importer.
- `cloud_baseline`, `cloud_snapshot`, `cloud_write_auth`, `cloud_upsert`,
  `history_compare`, `history_publish` — детализация внутри cloud save.
- `return_total` — обработка после возврата до готовности открыть дневник,
  включая существующие задержки анимации. Загрузка самой главной страницы после
  перехода сюда не входит. Этапы вложены и местами параллельны: их нельзя просто
  складывать. Статус `ok` означает успешное завершение измеряемой операции.

В случае ошибки кнопку копирования получает только специально включённый режим.
Ручное открытие дневника после замера повторно проверяет текущий сеанс.

## Локальное сравнение CPU

Node.js 24.19.0, синтетический экспорт 36 недель / 1080 уроков / 236209 байт,
хранилище в памяти, пять чередующихся прогонов. Сравнивалась последовательность
parse → save → read → save с cloudPending=false → read → read.
Медиана до повторного использования разбора — 236,8 мс, после — 87,0 мс.
Полных разборов — 6 → 1. Это только CPU указанной последовательности,
не замер Safari, сети или полной пользовательской синхронизации (~20 секунд
по наблюдению пользователя). Фактический выигрыш на iPhone ещё не измерен.
